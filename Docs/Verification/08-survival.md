## Tick, timing and terminal boundary

1. Gate on ownership/Playing/prepared/not already stepping and validate delta. Preserve the existing required-fuel then road preflight/rollback before travel; a diagnosed failure pauses before movement/drain. This safety reservation can rent target coverage before contact dispatch, as in Tasks05–07.
2. Inside IsStepping: consume buffered input, predict the player and all traffic/pickups with existing pose APIs, collect the shared segmented relative sweeps, and dispatch **TOI → pickup before obstacle on an exact tie → stable long spawn sequence**. The once-per-activation guard precedes all reward/damage events. EndDispatch flushes captured-token returns and clears contacts before commit.
3. Commit player/interactable logical poses. Record elapsed playing time and absolute distance once from actual logical travel, then call the existing ProgressionSystem.RecomputeScore. Coin events still use the established immediate recomputation; no duplicate +100 or second score owner is introduced.
4. StepFuel uses the tick's dt after rewards, then refreshes survival/grace debug values from the committed elapsed time. VehicleVisuals.FinishTick reconciles its contact-time flash deadline with that same playing clock.
5. Evaluate once: Lives if lives<=0; else Fuel if fuel<=0. A same-tick swept can restores before drain and rescues fuel. A coin on a terminal tick remains in the final score. Contacts can continue after the final accepted hit; pickups later in documented TOI order still apply before resolution.
6. Only a continuing run fills plans, maintains/spawns optional content, rebases, and publishes its one coherent tick snapshot. A terminal tick releases IsStepping after commit/drain, invokes guarded GameManager.EndRun once, sets actual speed0, holds poses, clears pending lane input, commits GameOver/timeScale0, publishes the final snapshot, then StateChanged and RunEnded(snapshot,reason). Cruise speed is retained for lifecycle use. Existing leases remain visible until Restart or authorized cleanup. Repeated Step/EndRun, stale interactions and reward calls cannot change the final data or rent content.

Fuel uses authored **100 capacity/start, 2 units/playing second, +30 per can**. Double accumulation avoids repeated float subtraction. Drain clamps remaining fuel <=**1e-4 units** to zero: at baseline this is at most **50 microseconds**, covering both the 2.24e-6-unit error from 2,500 float .02s steps and the observed native fixedDeltaTime .019999992102384567 (3.95e-5 fuel error across 2,500 ticks). Tests cover .01/.02/.1/.5s steps, assert positive fuel before the final tick, zero afterward, no negative fuel and elapsed50s within **5e-6 seconds** for passed float steps and **5e-5 seconds** for Unity's actual native fixed delta. Snapshot Fuel is a presentation float, not the accumulator. The fixture setter rejects invalid ranges; restore/drain clamp.

Step(0) returns false without consuming input, ticking, evaluating or preflighting. While running, negative/NaN/infinite delta throws ArgumentOutOfRangeException before mutation; outside Playing it remains a gated false return. Internal DrainFuel/StepFuel reject invalid delta and treat zero as no-op. No wall-clock, timeScale trick or origin shift advances survival. Grace is contact PlayingTime+authored **1.0s**; a **1e-6s** comparison allowance covers float TOI quantization at expiry. A contact about20 microseconds before expiry is rejected; the deadline is accepted. Encountered overlap never becomes delayed damage, including after the deadline.
